# PR 리뷰 답변

대상 PR: $ARGUMENTS (비어 있으면 0단계에서 내 PR 들을 훑어 고른다)

이 플러그인의 에이전트와 스킬은 `mm-harness:` 이름공간 아래에 있다. 에이전트를 부를 때는 `mm-harness:ai-designer` 처럼 이름공간을 붙인다.

판단 원칙은 `superpowers:receiving-code-review` 를 따른다. 리뷰어 말을 그대로 따르지도, 방어하지도 않는다. 코드로 확인하고 판정한다.

## 0. 나한테 달린 리뷰 모으기 (번호를 받지 않았을 때)

어느 PR 에 리뷰가 달렸는지 사람이 찾지 않아도 되게, 내가 연 PR 전부에서 아직 답하지 않은 리뷰를 모아 보여 준다.

1. 나(`gh api user -q .login`)를 확인하고 내가 연 열린 PR 을 모은다:
   ```bash
   gh pr list --author @me --state open --limit 50 --json number,title,headRefName,baseRefName,updatedAt,url
   ```
2. PR 마다 2단계와 같은 방법으로 **답할 거리**를 모은다: 해결되지 않았고 마지막 코멘트가 내가 아닌 인라인 스레드, 내 마지막 활동 뒤에 달린 리뷰 본문(빈 본문 제외)과 일반 코멘트. 봇은 뺀다. 답할 거리가 없는 PR 은 목록에서 뺀다.
3. 사용자에게 보여 준다. 먼저 PR 단위 표:

   | 선택 | PR | 묶음 위치 | 리뷰어 | 답할 거리 (인라인/본문) | 가장 오래된 것 | 
   |---|---|---|---|---|---|
   | ✅ | #289 제목 | 중심 (base develop) | @login | 2 / 0 | 2일 전 |

   - 묶음 위치: base 가 `develop` 이면 "중심", 다른 feature 브랜치면 "세부 (#<base 의 PR> 위)".
   - 추천 순서는 중심 PR 먼저, 그다음 오래된 순. 기본으로 전부 선택해 둔다.
   그 아래 PR 마다 **리뷰 내용을 한 줄씩** 보여 준다: `파일:줄` (인라인이면), 리뷰어, 심각도 머리표가 있으면 그대로(`[should-fix]` 등), 지적 한 줄 요약. 원문이 길면 요약하되 뜻을 바꾸지 않는다.
4. 사용자가 PR(또는 지적)을 고르면 고른 PR 마다 1단계부터 차례로 처리한다. 아무것도 고르지 않으면 끝낸다. 답할 거리가 하나도 없으면 "답할 리뷰 없음"과 확인한 PR 목록을 보고하고 끝낸다.

## 1. 준비

- `git status` 가 깨끗하지 않으면 멈추고 묻는다.
- `gh pr view <N> --json headRefName,baseRefName,state,url` 로 PR 브랜치를 확인하고 체크아웃한 뒤 `git pull` 한다. PR 이 열려 있지 않으면 멈춘다.

## 2. 리뷰 모으기

아직 해결되지 않았고 우리가 답하지 않은 것만 모은다.

- 인라인 스레드 (해결 여부 포함):
  ```bash
  gh api graphql -f query='query($o:String!,$r:String!,$n:Int!){repository(owner:$o,name:$r){pullRequest(number:$n){reviewThreads(first:100){nodes{isResolved isOutdated path line comments(first:50){nodes{databaseId author{login} body createdAt}}}}}}}' -F o=<owner> -F r=<repo> -F n=<N>
  ```
- 리뷰 본문과 일반 코멘트: `gh pr view <N> --json reviews,comments`
- `isResolved` 인 스레드, 마지막 코멘트가 우리(`gh api user -q .login`)인 스레드, 봇 코멘트는 뺀다.

## 3. 판정

지적마다 코드를 읽고 하나로 판정한다.

| 판정 | 기준 | 처리 |
|---|---|---|
| 반영 | 지적이 맞고 PR 범위 안 | 고친다 |
| 반박 | 코드·테스트·설계 근거로 지적이 틀림 | 근거를 단 답글 초안 |
| 질문 | 지적이 모호해서 판정 불가 | 되묻는 답글 초안 |
| 범위 밖 | 맞지만 이 PR 범위 밖 | 후속 이슈 제안 답글 초안 |

`shared/schemas.py`·BE 계약을 바꾸게 되는 지적은 판정과 상관없이 사람에게 넘긴다.

### 판정 확인 (사용자에게 한 번 보여 준다)

고치거나 답글을 달기 전에, 모은 리뷰와 판정을 한 표로 보여 주고 한 번 확인받는다. 사람이 리뷰 내용과 우리 대응을 보고 답할 수 있게 하기 위해서다.

| # | 위치 | 리뷰어 | 리뷰 요약 | 판정 | 할 일 (고칠 내용 또는 답글 초안) |
|---|---|---|---|---|---|

- 반박·질문·범위 밖은 이 표에서 답글 초안 전문을 같이 보여 준다.
- 사용자가 판정이나 초안을 바꾸라고 하면 바꿔서 다시 보인다. 확인되면 4·5단계를 진행한다. 이 확인 뒤에는 반영 답글을 따로 묻지 않는다.

## 4. 반영

- 한두 파일의 작은 수정은 메인 세션에서 직접 한다. 여러 파일에 걸치면 지적마다 `ai-implementer` 에게 브리프(지적 원문, 파일 경로, 판정 이유)를 넘긴다.
- 테스트로 드러나는 지적이면 실패하는 테스트부터 쓴다.
- 지적 하나에 커밋 하나: `fix(scope): 리뷰 반영 - <요약>`.
- 다 고친 뒤 전체 pytest (`ai/` 안에서 `.venv/bin/python -m pytest -q`) 통과를 확인하고 PR 브랜치에 push 한다.
- 이 PR 위에 쌓인 PR 이 있으면 고친 커밋을 위 브랜치들에 차례로 병합해 push 한다(히스토리 재작성 금지). 충돌이 나면 해결하고 그 브랜치의 전체 pytest 를 돌린다.

## 5. 답글

- **반영**: 판정 확인을 받았으면 고친 뒤 바로 단다. `반영했습니다 (<커밋 짧은 해시>): <무엇을 어떻게 바꿨는지 한 줄>`
- **반박·질문·범위 밖**: 판정 확인에서 승인받은 초안만 단다.
- 인라인 스레드 답글: `gh api repos/<owner>/<repo>/pulls/<N>/comments/<databaseId>/replies -f body='...'`
- 리뷰 본문·일반 코멘트 답글: `gh pr comment <N> --body '...'` 에 원 코멘트를 인용한다.
- 스레드를 resolve 하지 않는다. 해결 여부는 리뷰어가 정한다.
